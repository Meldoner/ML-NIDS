# Архитектура Network IDS (arc42)

## 1. Введение и цели

Проект развивается в два этапа: Phase 1 — курсовая работа 3 курса (MVP), Phase 2 — дипломная работа 4 курса с переходом к enterprise-уровню. В Phase 1 цель — показать работоспособный rule-based IDS с минимальной инфраструктурой. В Phase 2 цель — эволюция в ML-driven IDS с масштабируемой, отказоустойчивой и наблюдаемой архитектурой.

Контекст обучения:
- Phase 1 фокусируется на демонстрации базовой детекции и инженерного качества кода.
- Phase 2 фокусируется на промышленной архитектуре, масштабировании и полноценной наблюдаемости.

Ключевые цели Phase 1:
- Сбор сетевого трафика на агенте и передача агрегированных данных в анализатор.
- Детект rule-based угроз (порт-скан, SYN flood, большой ICMP, UDP/ICMP flood, горизонтальный и мульти-таргет скан, SYN/ACK дисбаланс, аномальные TCP флаги).
- Простая наблюдаемость через InfluxDB и Grafana.

Ключевые цели Phase 2:
- Подключение ML-модуля для обнаружения аномалий.
- Масштабирование аналитического контура и распределенное состояние.
- Переход на промышленный стек наблюдаемости.

Стейкхолдеры:
- Текущий пользователь: разработчик (автор курсовой).
- Потенциальные будущие пользователи: администратор инфраструктуры, аналитик безопасности.

## 2. Архитектурные ограничения

- Совместимость Phase 1 и Phase 2: базовые интерфейсы и контракты должны сохраняться и расширяться, а не ломаться.
- Языки и рантайм: Python 3.10+ для агентской и серверной части.
- Анализатор должен работать в контейнере (Phase 1 — Docker, Phase 2 — Kubernetes).
- Агент разворачивается как системный сервис на Linux и требует прав на захват пакетов.
- Агент устанавливается на сервере с инфраструктурой (например, сайт) и наблюдает трафик этого сервера.
- Инфраструктура наблюдаемости и хранения должна быть заменяемой без изменения core-логики детектирования.

## 3. Контекст и границы системы

Система анализирует трафик, наблюдаемый на сетевых интерфейсах сервера с агентом. Внутри границ системы находятся: захват пакетов, агрегация потоков, детектирование, запись в хранилище и визуализация. Вне границ — внешние сервисы и клиенты, генерирующие трафик.

Бизнес-контекст:
- Вход: сетевые пакеты на интерфейсах хоста (например, eth0).
- Выход: алерты и метрики в InfluxDB и отображение в Grafana.

Технический контекст (Phase 1):
- Agent -> Analyzer: HTTP/JSON батчи.
- Analyzer -> InfluxDB: запись алертов и метрик.
- Grafana -> InfluxDB: чтение для дашбордов.

Технический контекст (Phase 2):
- Analyzer -> ML Service: gRPC.
- Analyzer -> Redis: распределенное состояние.
- Observability stack: Prometheus + логирование + трейсинг.

## 4. Стратегия решения

Phase 1:
- Python выбран из-за скорости разработки, зрелости библиотек для сетевого анализа и ML.
- FastAPI обеспечивает простой HTTP API и четкий контракт.
- Детекторы разделены на правила; это облегчает расширение и тестирование.
- Flow-агрегация на агенте снижает нагрузку на сеть и анализатор.

Phase 2:
- gRPC выбирается для низкой латентности и строгих контрактов между анализатором и ML.
- Redis используется как распределенное состояние для счетчиков и окон.
- Kubernetes обеспечивает масштабирование и отказоустойчивость.

## 5. Представление строительных блоков

### 5.1. Уровень 1: системные блоки

- Agent: захват пакетов, агрегация потоков, отправка батчей.
- Analyzer: прием батчей, детектирование, генерация алертов.
- InfluxDB: хранение алертов и метрик трафика.
- Grafana: визуализация и дашборды.

### 5.2. Уровень 2: внутренние компоненты

Agent:
- SnifferEngine: захват пакетов с интерфейса и фильтрация.
- FlowAggregator: агрегация пакетов в короткие flow-записи и метрики.
- AgentReporter: отправка батчей по HTTP, базовый retry.

Analyzer:
- API слой: прием батчей и валидация.
- RuleEngine: выполнение набора правил и генерация алертов.
- InfluxDBWriter: запись алертов и метрик.

Набор правил Phase 1:
- SynFloodRule
- SynAckImbalanceRule
- PortScanRule
- HorizontalScanRule
- MultiTargetScanRule
- UdpFloodRule
- IcmpFloodRule
- LargeIcmpRule
- TcpFlagAnomalyRule

Будущие компоненты Phase 2:
- MLEngine: ML-детектор аномалий (внешний сервис).
- gRPC Adapter: интерфейс для связи с ML-сервисом.
- RedisCache: распределенное состояние и окна.

## 6. Представление выполнения (runtime view)

Сценарий 1: нормальная обработка трафика
1. Agent захватывает пакеты на интерфейсе сервера.
2. FlowAggregator объединяет пакеты в короткие агрегированные записи.
3. AgentReporter отправляет батч в Analyzer по HTTP.
4. Analyzer валидирует данные и передает их в RuleEngine.
5. RuleEngine вычисляет пороги на агрегатах (packet_count, syn_count, ack_count, payload_bytes).
6. RuleEngine возвращает алерты (если сработали правила).
7. InfluxDBWriter пишет алерты и метрики.
8. Grafana визуализирует данные.

Сценарий 2: срабатывание правила SYN flood
1. Внутри окна RuleEngine фиксирует превышение порога SYN.
2. Создается Alert с метаданными (syn_count).
3. Alert сохраняется в InfluxDB и отображается в Grafana.

Сценарий 3: временная недоступность анализатора
1. Agent не получает успешного ответа.
2. Батч временно остается в буфере, выполняется повторная отправка.
3. При переполнении буфера происходит дроп самых старых записей.

## 7. Представление развертывания

Phase 1:
- Analyzer разворачивается в Docker контейнере.
- InfluxDB и Grafana поднимаются через docker-compose.
- Agent устанавливается на Linux как systemd сервис на сервере приложения.

Phase 2:
- Analyzer, ML-сервис и InfluxDB разворачиваются в Kubernetes.
- Analyzer и ML-сервис размещаются в отдельных Deployments и Services.
- Redis кластер используется для распределенного состояния.
- Observability stack подключается как отдельный набор сервисов.

## 8. Сквозные концепции

Данные и модели:
- Входные записи: flow-записи с атрибутами источника, назначения, флагов и метрик.
- Ключевые агрегаты: packet_count, payload_bytes, syn_count, ack_count.
- Алерты: правило, уровень важности, сообщение, метаданные.

Состояние:
- Phase 1: локальные in-memory структуры в RuleEngine.
- Phase 2: Redis как распределенный state store для счетчиков и окон.

Наблюдаемость:
- Phase 1: InfluxDB + Grafana для алертов и метрик.
- Phase 2: Prometheus для метрик, централизованный сбор логов, распределенный трейсинг.

Безопасность и конфигурация:
- API ключ для базовой аутентификации в Phase 1.
- Перенос секретов в безопасные хранилища (K8s Secrets, Vault) в Phase 2.

Время:
- Система использует Unix timestamp; синхронизация времени важна для корректных окон.

## 9. Архитектурные решения (ADR)

ADR 001: gRPC для ML-сервиса
- Контекст: требуется низкая латентность и строгие контракты между анализатором и ML.
- Решение: использовать gRPC вместо REST в Phase 2.
- Последствия: требуется protobuf-описание контракта и инфраструктура gRPC.

ADR 002: Redis для распределенного состояния
- Контекст: in-memory состояние не масштабируется на несколько реплик.
- Решение: использовать Redis кластер для счетчиков и окон.
- Последствия: внешняя зависимость на state store, повышенная масштабируемость.

## 10. Требования качества

Приоритеты качества:
- Масштабируемость: возможность увеличивать число анализаторов без изменения протоколов.
- Надежность: устойчивость к кратковременным сбоям сети и недоступности анализатора.
- Безопасность: базовая аутентификация и минимизация доступа к API.

Примеры качественных сценариев:
- Система продолжает принимать батчи при кратковременной недоступности InfluxDB.
- Добавление ML-модуля не требует изменения API агента.
- Наблюдаемость позволяет выявить и объяснить причину срабатывания.

## 11. Риски и технический долг

- In-memory состояние RuleEngine может теряться при перезапуске анализатора.
- Агрегация flow снижает точность некоторых правил по сравнению с сырой телеметрией.
- Отсутствие TLS в Phase 1 ограничивает безопасность в открытых сетях.
- Недостаточные данные для выбора оптимальной ML модели.

## 12. Глоссарий

- Flow: агрегированная запись по ключу (src/dst IP, порты, протокол) за короткое окно.
- RuleEngine: модуль rule-based детекции.
- MLEngine: ML модуль детекции аномалий (Phase 2).
- SYN flood: атака с большим числом SYN без завершения рукопожатия.
- Port scan: перебор портов на целевом хосте.
- SPAN/TAP: зеркалирование трафика на отдельный порт для мониторинга.
